# Xing4.0-29B-Intent · 游戏 NPC 意图理解评测

奥德赛（Odyssey）主题开放世界 RPG 的 NPC 对话意图评测套件。

目标：在把它接进 NPC 系统之前，先量化三个问题——
**意图分得准不准**、**参数填得对不对**、**会不会在不该动手时乱动手**。

---

## 为什么是奥德赛主题

模型的 275 万条训练语料覆盖 19 个领域，SLU 部分（96.9 万条）主要来自
MTOP、ATIS、Snips、MASSIVE——旅行、餐厅、手机助手域。

中文里"码头""灯塔""淡水"几乎都在训练分布内；而"卡戎渡口""斯库拉海峡"
"埃俄罗斯岛"是彻底的分布外专有名词。

> **用模型见过的词去测，等于没测。**
> 奥德赛词表测的是真实上限，通用岛词表测的是"schema 与内容错配"的下限。
> 本仓库保留 `schema-island-generic.json` 作对照（29 类、无「查询神谕」、通用词表）。
> **已实跑对照（11-07，同 227 条用例）**：奥德赛 schema 92.1% vs 通用岛 68.7%——
> 分差含神谕类整类缺失的结构性成分，但方向明确：**schema 词表与描述必须随章节内容
> 演进，不能通用复用**（详见 `results/README.md`）。

神话还自带**成对的易混实体**（斯库拉 / 卡律布狄斯、雅典娜 / 赫尔墨斯 / 波塞冬），
这不是硬凑的干扰项，是玩家真的会混的一对。

## 快速开始

```bash
# 1. 冒烟测试：不联网，用黄金答案自检打分管线
python eval.py --backend mock

# 2. 天翼平台实跑（免 GPU，推荐先走这条）
export TELEAI_API_KEY=sk-xxx
python eval.py --backend teleai --out result-teleai.json

# 3. 本地部署实跑
python eval.py --backend local --base-url http://localhost:8000/v1 \
               --model Xing4.0-29B-Intent --out result-local.json
```

常用参数：

```bash
--group confuse,negative   # 只跑指定分组
--limit 20                 # 只跑前 N 条
--workers 8                # 并发
--verbose                  # 打印模型原始输出
```

### 本地端点形态

`--backend local` 兼容三种常见形态：

| 运行时 | base-url | 备注 |
|---|---|---|
| vLLM / SGLang | `http://localhost:8000/v1` | 需装 xing4 插件 |
| LM Studio | `http://localhost:1234/v1` | 加载 GGUF 后直接起服务 |
| Ollama | `http://localhost:11434/v1` | 加 `--ollama` 走其原生 option |

GGUF 量化版（17.8GB，`xing4_0-29b-intent-iq4_nl.gguf`）配合 LM Studio
或 Ollama，单张 24GB 卡可跑。

### 自检端点

`fake_server.py` 是一个模拟 OpenAI 兼容端点，用于在拿到真实凭据前
验证整条链路（请求构造 → 响应解析 → 打分 → 混淆统计）：

```bash
py -3 fake_server.py 8731
py -3 eval.py --backend local --base-url http://localhost:8731/v1 --limit 40
```

它按"中等水平模型"的规律造错（类别准确率约 80%、参数填全率约 70%、
少量负例误触发），因此分数偏低是**预期行为**——它验证的是链路而非模型。

## 指标定义

| 指标 | 含义 | 游戏侧后果 |
|---|---|---|
| **类别准确率** | category 集合完全命中 | 走错对话分支 |
| **参数级 F1** | 逐 category 桶算 F1 后平均 | 填错数值/物品/地点 |
| **完全正确率** | category + args 全对 | 该动作完全走不通 |
| **负例误触发率** | 该落「其他意图」却没落 | **最致命**：NPC 误触发交易/任务 |
| **延迟分位** | P50 / P90 / P99 | 对话节奏是否拖沓 |

分类别统计了类别分和参数分，因为二者的失败后果不同：
类别错 → 走错分支；参数错 → 填错数值。官方评测里类别分 69 是**低于**
Gemini-3.6-Flash 的 71，优势全在参数——游戏里后者同样是致命伤
（把"我要三瓶药"填成"我要三瓶油"，玩家会立刻发现）。

参数比对采用**值级 exact match**：值必须完全相同才算命中，
避免部分给分掩盖"填错值"这类硬伤。

| 分组 | n | 考察什么 |
|---|---:|---|
| `clear` | 64 | 明确单意图，基础能力基线 |
| `confuse` | 24 | **神话实体消歧**：塞壬/斯库拉/卡律布狄斯、众神 vs 英雄、人名 vs 地名 |
| `boundary` | 22 | **类别边界**：购买/价格/库存，导航/地点信息/附近目标，神谕 vs 任务线索 |
| `slot_missing` | 18 | 参数缺失时必须留空，不得编造 |
| `chitchat` | 14 | 闲聊与告别，含"我还能回家吗"这类边界闲聊 |
| `oov` | 14 | **分布外专有名词** + 系统指令越界（"切换到第一人称"） |
| `hades_oov` | 16 | **第二章冥界词表 OOV 回归**：献祭沟/蜂蜜酒/特瑞西阿斯/亡魂/长路捷径——v0.2.0 发版判据组（每实装一章必加一组，见 PRODUCT §8）；11-07 傍晚增补 hades_15「俄刻阿诺斯之岸」/hades_16「献祭之沟」变体（判据仍按 v4 的 14 条时点计：85.7% RED） |
| `wind_oov` | 14 | **风神岛插章词表 OOV 回归**：风神岛/埃俄罗斯/风袋/十二风/风向/把风停了——同 PRODUCT §8 纪律，每实装一章必加一组（v4 首跑 100%） |
| `ch3_oov` | 14 | **第三章声之海词表 OOV 回归（已加组，待首跑）**：塞壬海域/蜡/桅杆/歌词残页/卡律布狄斯/斯库拉——schema 尚无蜡/桅杆/歌词残页词表，首跑大面积翻车属流程预期（"加组→首跑→归因→补 schema→复测"） |
| `multi` | 13 | 一句话多意图，含同类别多次出现 |
| `negative` | 12 | 乱码、噪声、纯测试文本 |
| `multiturn` | 12 | 多轮指代消解（"三罐"、"塞壬"、"矛"） |
| `hostile` | 8 | 威胁与攻击 |
| `state_set` | 12 | **状态型 vs 设定型**：查询血量 vs 修改血量，混合 schema 时的高危项 |

`state_set` 这一组是重点。第三方实测中模型曾把"已有状态"当成"要设定的值"
（车窗开合位置返回 0%）。游戏里这会变成"把血量调到八十"被误判成查询、
或"我还有多少水"被误判成指令。

## Schema 设计要点

**1. 状态型与设定型分离。**
`查询自身状态`（饥饿/口渴/体力/伤势）与 `使用消耗品`、`营地准备` 明确分开，
description 里写死"本类只做状态读取，绝不包含修改状态的含义"。

**2. 枚举 vs 自由文本，按可枚举性划分。**
可枚举的（物品标准名、货币、装备部位、任务类型）给封闭列表 + 精确匹配；
不可枚举的（目的地、任务名称、接收方）用"保留玩家原话说法，不要强行归并"。

**3. 专有名词保留原文。**
`目的地` 的 description 明确写"这是神话世界中的专有名词，不要强行归并到
标准名称，玩家怎么称呼就怎么输出"。模型填出 `斯库拉` 而非 `斯库拉海峡`，
在游戏里反而是对的——归一化是游戏代码的活，不是模型的活。

**4. 兜底类别必设。**
`其他意图` 的 description 要求"必须诚实归入本类，不要强行匹配"。
NPC 场景下，负例处理比正例命中率更影响体验。

**5. 系统指令越界。**
`其他意图` 显式覆盖"要求改变游戏系统状态、切换视角、打开界面、修改数值"，
避免玩家输入 `/open` 或"打开背包"时被当成 NPC 动作。

## 实测注意事项

**必须关闭深度思考。** 同一题从 <0.6s 涨到 2.6s。脚本已在
`chat_template_kwargs` 里设 `enable_thinking: false`。

**延迟按 ≥1.2s 规划。** 官方口径是 ≤200ms（中文），第三方端到端实测 334ms
（含公网与网关），本仓库 227 条全量实测 P50 866–1169ms（**时段波动大**，
同一 schema 隔天测出 1169 与 866ms；P99 最高 2836ms）——schema 描述加长有
准确率/延迟交易，见 `results/`。按 150–400ms 规划会低估。

**别开批量推理。** 托管 API 明确标注不支持。

**prompt 格式。** 天翼接口要求单条 `role:user` 消息，任务说明 + 完整 schema
+ 待测输入拼在同一条 content 里；system 消息由服务方预置，禁止传入。
本地 vLLM 若用官方 XingIntent SDK 则自带 system prompt，脚本的 local 后端
采用与天翼一致的单消息格式以保证两者可比。

**vLLM / SGLang 需要装插件。** `xing4_0` 架构以 out-of-tree 插件发布
（`xing4-vllm-plugin` / `xing4-sglang-plugin`），上游默认不识别。

## 接入建议

评测结果指向的架构是**双层**：

```
玩家输入
  ↓
[Xing4.0-29B-Intent]  语义解析层 → {category, args}
  ↓                            ↓ 低置信 / 落兜底
  ↓ 命中且参数校验通过          ↓
游戏逻辑执行              [通用大模型] 闲聊、人格、台词生成
```

把 Xing 当 System 1 路由器，通用模型当 System 2 对话生成器。
参数落地前**必须**过一次服务端校验（对照背包/任务状态），并做口语归一化
（模型会填"关掉"而不是"关闭"）。

## 调优建议

评测后如果某一组分数低，按这个顺序排查：

1. **先看混淆对**（脚本会输出 Top 15）——如果是两个类别的 description 重叠，
   改 schema 描述，而不是换模型。
2. **检查枚举列表**——若参数填错且总被归到某个标准值，说明枚举列表该扩。
3. **检查 description 是否留了歧义**——第三方实测中"两分类边界没写干净"
   直接导致 24 条错 1 条。
4. **最后才考虑微调**——275 万条语料 + schema 驱动的冷启动能力，
   多数问题靠改 schema 就能解决。

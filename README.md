# 奥德赛（Odyssey）· 游戏 + NPC 意图理解评测

一句话：这是《奥德赛》主题开放世界 RPG 的主仓库——**游戏本体**（`odyssey-witch/`）加上一套给 NPC 对话模型出的**"考卷"**（评测套件）。

游戏里 NPC 靠大模型听懂玩家输入：玩家说"买三瓶蜂蜜"，模型要解析成「购买 + 物品=蜂蜜 + 数量=3」。用的模型是 **Xing4.0-29B-Intent**。在把它真正接进游戏之前，先量化三件事：

1. **听得懂吗** —— 意图分类准不准（听错就走错对话分支）
2. **记得全吗** —— 参数（物品/数量/地点）填得对不对（把"三瓶药"填成"三瓶油"，玩家一眼识破）
3. **该闭嘴时闭嘴吗** —— 玩家闲聊、说乱码时，会不会误触发交易/任务（最伤体验）

## 快速开始

### 跑游戏

```
双击 odyssey-witch\启动游戏.bat
```

会自动起本地服务（默认 http://localhost:8765，需 `odyssey-witch` 或上级目录有 `key.txt`，即天翼 API key）。服务端分工：

- `/api/parse` —— Xing4.0-29B-Intent，把玩家输入解析成意图+参数
- `/api/chat` —— TeleChat3-438B-A24B，生成女巫人格台词

key 只留在服务端，绝不进浏览器。

### 跑评测

```bash
# 1. 冒烟测试：不联网、不花 key，自检打分管线
python eval.py --backend mock

# 2. 天翼平台实跑（免 GPU，推荐先走这条）
export TELEAI_API_KEY=sk-xxx
python eval.py --backend teleai --out result-xxx.json

# 3. 本地部署实跑（vLLM / LM Studio / Ollama 均可）
python eval.py --backend local --base-url http://localhost:8000/v1 --model Xing4.0-29B-Intent --out result-local.json
```

常用参数：`--group confuse,negative`（只跑某几组）、`--limit 20`、`--workers 2`（**别调高**，并发会触发 429 限流）、`--verbose`。

没有真实 key 时想验证链路，可以跑 `py -3 fake_server.py 8731` 再指向它——它按"中等水平模型"规律造错，分数偏低是预期行为。

## 考卷怎么设计的

### 为什么要用神话主题

模型的训练语料以通用助手/旅行/餐厅域为主，"码头""淡水"这类词它见过；
而"斯库拉海峡""埃俄罗斯岛"是彻底没见过的专有名词。
**用模型见过的词去测，等于没测**——所以考卷大量使用奥德赛神话专名，
还专门利用了神话自带的成对易混实体（塞壬/斯库拉/卡律布狄斯、雅典娜/赫尔墨斯/波塞冬），
这不是硬凑的干扰项，是玩家真的会混的词。

实测对照：同一批用例，换成通用词表的对照版 schema（`schema-island-generic.json`）
准确率从 92% 掉到 **68.7%**。结论：**schema 词表必须随游戏章节内容演进，不能通用复用**。

### 18 个分组一览（313 条）

| 分组 | n | 考察什么（大白话） |
|---|---:|---|
| `clear` | 64 | 正常单意图，基础基线 |
| `confuse` | 24 | 神话实体消歧（塞壬还是斯库拉？） |
| `boundary` | 22 | 相邻类别边界（问价格 vs 直接买） |
| `slot_missing` | 18 | 参数没说就必须留空，不许编 |
| `state_set` | 12 | **重点高危**：查血量（状态型）vs 调血量（设定型），混了会改玩家数值 |
| `multi` | 13 | 一句话多件事 |
| `multiturn` | 12 | 多轮指代（"再来三罐"——哪三罐？） |
| `chitchat` | 14 | 闲聊/告别，NPC 该陪聊而不是执行 |
| `negative` | 12 | 乱码、噪声、纯测试文本 |
| `hostile` | 8 | 威胁攻击性发言 |
| `oov` | 14 | 通用分布外名词 + 系统指令越界（"切换第一人称"） |
| `prologue_oov` 等 7 组 `*_oov` | 14~16/组 | **每实装一个游戏章节，就加一组该章节词表考题**（序章/冥界/风神岛/声之海/奥吉吉亚/斯克里岛/伊萨卡），防止新章节专名大面积听不懂 |

### 五个指标怎么看

| 指标 | 含义 | 出错的后果 |
|---|---|---|
| 类别准确率 | 意图分对了没 | 走错对话分支 |
| 参数级 F1 | 物品/数量/地点填对了没 | 数值/物品填错 |
| 完全正确率 | 类别+参数全对 | 动作整个走不通 |
| 误触发率 | 该兜底却乱执行 | **最致命**：NPC 乱卖东西/乱接任务 |
| 延迟分位 | P50/P90/P99 | 对话是否拖沓 |

## 目前测到什么水平

成绩单全部在 `results/`（每轮一份 summary 快照）。关键结论：

- **最新一轮（v9，2026-11-09，313 条全量）**：类别准确率 **92.97%**、参数 F1 89.2%、完全正确 74.4%、误触发 3.3% —— 守住 **类别 ≥90% 红线**

架构建议（实测数据支持）：**双层**——意图模型当"耳朵"（语义解析），通用大模型当"嘴"（人格台词）。

## 实测注意事项（跑之前必读）

1. **必须关深度思考**（脚本已内置 `enable_thinking: false`），否则延迟 ×5。
2. **并发 ≤2**，高了触发 429 限流；限流失败的条目用单并发补跑，别直接丢弃。
3. 天翼接口只收**单条 user 消息**（任务说明+schema+输入拼一条），system 消息由服务方预置。
4. 本地 vLLM/SGLang 需装官方插件（`xing4-vllm-plugin` 等），上游默认不识别该架构。
5. 每轮结果**用新文件名**保存，别覆盖旧 result；summary 快照同步进 `results/`。

## 分数低了怎么调（按顺序来）

1. **先看混淆对**（脚本输出 Top 15）——两个类别描述重叠就改 `schema.json` 的 description；
2. **再看枚举列表**——参数总被填成某个标准值，说明该扩清单；
3. **再查描述歧义**——边界没写干净是历史踩过最多的坑；
4. **最后才考虑微调模型**——绝大多数问题改 schema 就能解决。

## 给后续维护者（工作纪律）

- **每实装一章必加一组 `*_oov`**：加组 → 首跑 → 归因 → 补 schema → 复测 → summary 快照入库，一组都不能跳。
- schema 版本号在 `results/README.md` 按轮次维护（当前 v2.5.4 + 消耗品清单扩充补丁）；`schema.json` 本身不写版本字段。
- 旧章节考题要回归复跑：新章节上线后全量重跑一遍，确认老组不退化。
- 详细历史逐轮结论见 `results/README.md`。
